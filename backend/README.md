# Type-to-Run — backend (Express + MySQL)

The REST API that `react_game` and `flutter_game` both use. It owns all 10 tables. Clients never touch the database directly.

## Setup (XAMPP / MySQL / MariaDB)

```bash
cp .env.example .env        # set DB_USER / DB_PASSWORD (XAMPP: root / empty) and a JWT_SECRET
npm install
npm run db:reset            # creates DB_NAME if missing, (re)creates the 10 tables, loads the game content
npm run dev                 # http://localhost:3000/api  (restarts on file changes)
```

`npm run db:reset` **drops all game tables**, including players and progress. Only use it to set up or start over.

```bash
npm test                    # API tests against a real database: creates and DROPS `type_and_run_test`
```

The DB user needs rights to create the `type_and_run_test` database, or set `TEST_DB_NAME`. Requires MySQL 8.0.16+ or MariaDB 10.4+, which enforce the `CHECK` constraints.

## Layout

```
server.js                 Express app: mounts the three route files; listens when run directly
config/database.js        mysql2/promise pool + withTransaction()
routes/userRoutes.js      /api/users   — register, login, me, inventory        (USERS, USER_INVENTORY)
routes/ghostRoutes.js     /api/ghosts  — ghost catalogue + exorcism items       (GHOST_TYPE, GHOST_REQUIRED_ITEMS)
routes/gameRoutes.js      /api/game    — words, items, places, start, results   (the rest)
controllers/gameController.js   every handler, grouped by route file
middleware/auth.js        JWT sign/verify, requireAuth → req.userId                [added]
middleware/errors.js      HttpError, asyncHandler, 404 + error handler            [added]
services/gameRules.js     unlock checks, ritual requirements, transactional "Save Results"   [added]
services/rows.js          MySQL 0/1 → true/false, strips password hashes          [added]
database/schema.sql       DDL for the 10 tables (InnoDB, utf8mb4, FKs, UNIQUE pairs, CHECKs)
database/seed.sql         game content — GENERATED by ../react_game (npm run content)
scripts/resetDb.js        npm run db:reset
tests/api.test.js         end-to-end API tests (node:test + supertest)
```

`[added]` marks folders beyond your original layout. They keep `gameController.js` focused on request handling.

## API

All bodies are JSON and responses use the database's snake_case column names. 🔒 means the request needs `Authorization: Bearer <token>`.

| Method | Path | Body → Response |
|---|---|---|
| GET | `/api/health` | `{ ok: true }` |
| **userRoutes** | | |
| POST | `/api/users/register` | `{ username, email, password }` → `{ token, user }` (201; 409 if email taken) |
| POST | `/api/users/login` | `{ email, password }` → `{ token, user }` (401 if wrong) |
| GET 🔒 | `/api/users/me` | users row (no password) |
| GET 🔒 | `/api/users/me/inventory` | `[{ item_id, quantity }]` |
| **ghostRoutes** | | |
| GET | `/api/ghosts` | GHOST_TYPE rows |
| GET | `/api/ghosts/:id` | ghost + `required_items: [{ item_id, item_name, item_type, quantity_required }]` + `appears_in: [{ place_id, place_name, spawn_chance, is_boss }]` |
| **gameRoutes** | | |
| GET | `/api/game/words` | WORD_BANK rows |
| GET | `/api/game/items` | ITEMS rows |
| GET 🔒 | `/api/game/places` | `[{ place, progress \| null, unlocked }]` |
| GET | `/api/game/places/:id` | `{ place, ghosts[ghost_type + spawn_chance + is_boss], spawns, items, requirements }` |
| GET | `/api/game/places/:id/ritual` | `[{ item_id, quantity_required }]` for the place's boss |
| POST 🔒 | `/api/game/places/:id/start` | marks `in_progress` → progress row (403 if locked) |
| POST 🔒 | `/api/game/places/:id/results` | `{ outcome: extracted\|exorcised\|caught, wpm, accuracy, playtimeSeconds, collected: [{ item_id, quantity }] }` → progress row (409 if the ritual's items are missing) |

`POST /api/game/places/:id/results` runs in **one transaction**. It adds playtime. On `extracted` or `exorcised`, it also:
- banks the collected items, capped at what the place can spawn
- for `exorcised`, re-checks the ritual requirements on the server and consumes those items
- sets `cleared`, `exploration_completed` and `ritual_completed`, and keeps `best_wpm`/`best_accuracy` as maxima
- on the first clear, increments `total_locations_completed` and unlocks the next place

If anything fails, nothing is saved. On `caught`, only the playtime is recorded and the items are lost.

**Security notes:** passwords are bcrypt hashes and are never returned. Every player query is scoped to the token's user. Write endpoints validate their input. WPM and accuracy are computed on the client and range-checked here, so a modified client could still submit fake scores.
